# Notifications

Tell users about things that happened: "a new post was published", "a new
order was placed". Shown in the web panel (a bell with an unread count),
pushed live over a socket. Email is planned, not built.

Other contexts never write notifications. They publish domain events
(`PostPublishedEvent`, `OrderPlacedEvent`); the notification context handles
them, decides who to tell, and stores one row per recipient.

## Tables

```sql
CREATE TABLE notifications (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    recipient_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,

    -- What happened: 'post.published' or 'order.placed'. Allowed values and
    -- their data shape are checked in the domain (NotificationData).
    type         VARCHAR(64) NOT NULL,
    -- Facts needed to render it, not the rendered text, so wording and
    -- language can change later: {"postId": "5", "title": "Hello", "path": "/hello"}
    -- No default: every type always writes its data.
    data         JSONB NOT NULL,
    -- Who caused it; NULL for the system
    actor_id     BIGINT REFERENCES users(id) ON DELETE SET NULL,

    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- NULL means unread
    read_at      TIMESTAMPTZ
);

-- The bell: newest first per recipient (the list actually orders by id DESC)
CREATE INDEX ON notifications (recipient_id, created_at);
-- The unread count
CREATE INDEX notifications_unread
    ON notifications (recipient_id) WHERE read_at IS NULL;
-- ON DELETE SET NULL of the actor
CREATE INDEX ON notifications (actor_id);
```

Index names other than `notifications_unread` are generated by the planner
(with a hash suffix). The migration also has a plain `(recipient_id)` index
from the relation.

### Example rows

|  id | recipient_id | type           | data                                              | actor_id | read_at |
| --: | -----------: | -------------- | ------------------------------------------------- | -------: | ------- |
|   1 |          124 | post.published | {"postId":"5","title":"Hello","path":"/hello"}    |      123 |         |
|   2 |          124 | order.placed   | {"orderId":"9","total":"125000","currency":"VND"} |      130 | 2026-…  |

## Events

- `post.published`: `PublishPostHandler` raises `PostPublishedEvent` after
  saving, only when the post is live now (not scheduled).
  `PostPublishedNotifier` notifies every active, non-deleted user except the
  publisher.
- `order.placed`: `PlaceOrderHandler` raises `OrderPlacedEvent`;
  `OrderPlacedNotifier` notifies active `admin` and `editor` users except the
  buyer. `total` is in minor units.

## Flow

1. A command saves its change, then publishes an event on the in-process
   `EventBus`.
2. The notifier lists recipients (`ListActiveUserIdsQuery`, optional roles),
   `fanOut` drops the actor and duplicates, and `createMany` inserts the rows.
3. Each stored row is pushed to its recipient's socket as `notification`.
   Failures are logged, never surfaced to the publishing request.

## Api

- `GET /notifications?limit=&before=` (newest first, `limit` 1-50, default
  20; `before` is an id cursor). Returns `{ items, unread, nextCursor }`, so
  there is no separate unread-count route.
- `POST /notifications/:id/read`, `POST /notifications/:id/unread`,
  `POST /notifications/read-all`
- `DELETE /notifications/:id`, `DELETE /notifications/read` (clear read ones)

Items carry `actor: { id, name } | null` (name is the user's `short_name`,
else `display_name`, read at list time, so renames show) and `read: boolean`.

## Realtime

- socket.io namespace `/realtime` on the api. The browser never holds an
  access token (HttpOnly cookies on the web server), so it connects with a
  one-minute ticket from `POST /auth/ws-ticket` (its own JWT type and key),
  fetched by a server action, fresh on every reconnect.
- The socket joins `user:<id>` and only receives: `notification`,
  `notification:read`, `notification:unread`, `notification:read-all`,
  `notification:deleted`, `notification:cleared-read` (the last five keep
  other tabs in sync). Bad tickets get `error:auth` and are disconnected.
- The web bell (`apps/web/src/components/notifications`) loads the list once
  and then follows the socket; no polling.
- Allowed origins: `WEB_ORIGINS` (comma separated); any origin when it is
  unset. The ticket is what authorizes.
- One api process: rooms live in memory. Several instances need the
  socket.io Redis adapter.

## Notes

- Render text at read time from `type` + `data` (clients do), so old
  notifications follow wording changes; keep `data` small and free of
  secrets.
- `data` can point at things that were since deleted; render a fallback.
- Recipients are users; a soft delete leaves rows, a hard delete cascades.
- Group bursts ("3 new comments") at read time, not by merging rows.

## Not built yet

- `notification_preferences` (per user and type: `in_app`, `email`; no row
  means the type's default) and `GET` / `PUT /notifications/preferences`.
- `notification_emails` outbox, written in the same transaction as the
  notification, and an email worker claiming pending rows with
  `FOR UPDATE SKIP LOCKED`, retrying with backoff, then `failed`. Don't email
  disabled or deleted users.
- `UserRoleChanged` event (`user.role_changed`: "you are now an editor").

## Open questions

- Retention: delete read notifications after, say, 90 days?
- Email digest (one daily summary) instead of one email per notification?
- Events are in-process and published after the save: a crash between commit
  and handler loses the notification. Move to an outbox if that matters.
